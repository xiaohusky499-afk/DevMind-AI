# DevMind AI RAG 性能优化与并发评测报告

评测日期：2026-08-28  
环境：Windows 本机、CPU 推理、PostgreSQL 16、Milvus、BGE-M3、BGE Reranker、DashScope LLM。

## 1. 优化目标与约束

- 优先降低正式问答链路延迟。
- 不降低可信度阈值，不以增加错误回答换取速度。
- 继续保持无答案拒答、引用溯源和来源准确性。
- 先定位真实瓶颈，再实施最小范围修改。

## 2. 分阶段耗时基线

固定 10 条技术问题优化前平均耗时：

| 阶段 | 平均耗时 |
|---|---:|
| Query Rewrite | 3.41 s |
| Embedding | 0.71 s |
| Milvus | 0.009 s |
| Reranker | 13.14 s |
| LLM 完整生成 | 3.56 s |
| 端到端 | 20.86 s |

Reranker 占端到端时间约 63%，Query Rewrite 次之。PostgreSQL、Milvus 和引用持久化不是当前瓶颈。

## 3. 实施内容

1. 在检索响应和消息 `usage JSONB` 中增加 Query Rewrite、Embedding、Milvus、Reranker、首字、LLM 和总耗时。
2. 无历史的独立问题直接使用原问题检索，只有依赖上下文的追问才调用 LLM 改写。
3. 正式配置从 5 个召回片段中选择前三个进入 Reranker；评测集显示所有正确证据均位于召回 Top-2。
4. BGE-M3 和 Reranker 使用线程安全的单例及推理锁，防止并发重复加载或同时访问非线程安全模型。
5. 本地模型、外部 LLM 增加并发上限、阶段超时和背压。
6. WebSocket 中断可正确标记消息失败，并兼容客户端断开时的关闭异常。
7. 增加 `BGE_DEVICE=cuda` 部署开关；Reranker 已能自动使用 CUDA。

## 5. 并发压测

| 并发 | 成功率 | p50 | p95 | 吞吐量 | 峰值内存 |
|---:|---:|---:|---:|---:|---:|
| 1 | 100% | 14.52 s | 14.52 s | 0.069 RPS | 3.66 GB |
| 10 | 100% | 37.61 s | 67.54 s | 0.148 RPS | 3.71 GB |
| 20 | 100% | 173.76 s | 283.69 s | 0.070 RPS | 3.72 GB |
| 50 | 未执行 | - | - | - | - |

20 并发已经超过 120 秒饱和线，因此按计划停止 50 并发。服务在饱和时没有请求错误或内存失控，但 CPU Reranker 队列造成不可接受的等待时间。

## 6. 结论

- 当前 CPU 单实例适合开发、演示和低并发 Pilot，不满足 50 并发 p95 小于 5 秒的生产目标。
- 继续调大本地线程数不会解决问题，反而会让多个 Torch 推理任务争抢 CPU。
- 生产环境下一步应将 BGE-M3 与 Reranker 部署到 GPU，或拆分为独立推理服务并水平扩容。
- 完成 GPU 部署后，应复用同一评测脚本重新执行 40 条质量回归以及 1/10/20/50 并发压测。
