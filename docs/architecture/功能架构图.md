# DevMind-AI 功能架构与实现详图

> 本文以当前仓库代码为事实来源。系统形态是“React 前端 + FastAPI 模块化单体 + 独立文档 Worker”，问答生成目前在 WebSocket 请求进程内执行；文档任务由 PostgreSQL 任务表驱动，而不是 Redis Streams。

## 3. 智能问答主链路

```mermaid
sequenceDiagram
    actor User as 用户
    participant UI as React 工作台
    participant API as FastAPI
    participant PG as PostgreSQL
    participant Redis as Redis
    participant RAG as RAG Service
    participant Milvus as Milvus
    participant Ranker as BGE Reranker
    participant LLM as DashScope LLM

    User->>UI: 提交问题
    UI->>API: POST /api/v1/messages
    API->>PG: 写入用户消息和待处理助手消息
    API->>Redis: 写入一次性 stream ticket
    API-->>UI: assistant_message_id 和 stream_url
    UI->>API: WebSocket /api/v1/chat/stream
    API->>Redis: 原子 GETDEL 校验 ticket
    API->>PG: 抢占 pending 消息并读取上下文
    API->>RAG: answer_events
    RAG->>PG: 计算可访问知识库与文档集合
    RAG->>RAG: 多轮问题改写
    RAG->>Milvus: 按 KB 和文档 ID 混合检索
    Milvus-->>RAG: 稠密加稀疏召回结果
    RAG->>Ranker: 对候选片段重排序
    Ranker-->>RAG: Top N 证据
    RAG->>PG: 保存检索运行 结果 审计和引用
    RAG->>RAG: 证据筛选与可信度计算
    alt 有足够证据
        RAG->>LLM: 上下文 历史 问题
        LLM-->>RAG: 流式 Token
        RAG-->>UI: status retrieval citations token
    else 无足够证据
        RAG-->>UI: 知识不足的确定性回答
    end
    RAG->>PG: 保存答案 用量 时延 可信度
    RAG-->>UI: final
```

实现要点：

- `POST /messages` 只创建消息与一次性流式票据；真正的检索和生成在随后建立的 WebSocket 连接内执行。
- `stream_ticket` 存在 Redis，TTL 为 300 秒，并通过 `GETDEL` 保证只能使用一次。
- 检索前先根据组织、知识库成员角色、用户团队和安全等级计算允许访问的知识库与文档 ID，再把 ID 过滤条件传给 Milvus。
- 检索结果、重排结果、引用、最终回答、Token 用量和各阶段耗时均落 PostgreSQL。
- 断流或生成异常会更新消息状态，客户端可通过消息接口重新读取结果或观察失败状态。

## 4. 文档入库与索引链路

```mermaid
sequenceDiagram
    actor Editor as 知识库编辑者
    participant API as FastAPI
    participant Scan as 文件安全服务
    participant ClamAV as ClamAV
    participant MinIO as MinIO
    participant PG as PostgreSQL
    participant Worker as 文档 Worker
    participant Loader as Document Loader
    participant Splitter as Recursive Splitter
    participant Embed as BGE M3
    participant Milvus as Milvus

    Editor->>API: 上传 PDF DOCX MD YAML JSON
    API->>PG: 校验知识库 editor 权限
    API->>Scan: MIME 后缀 文件结构 大小校验
    Scan->>ClamAV: 病毒扫描
    API->>API: SHA256 去重
    API->>MinIO: 保存原始文件
    API->>PG: 创建 document 和 document_task
    API-->>Editor: document_id task_id uploaded
    loop 轮询待执行任务
        Worker->>PG: FOR UPDATE SKIP LOCKED 抢占任务
    end
    Worker->>PG: 建立租约并周期心跳
    Worker->>MinIO: 下载原始文件
    Worker->>Loader: 按格式解析
    Loader->>Splitter: 递归切分并保留页码等元数据
    Splitter->>PG: 保存 document_chunks
    Splitter->>Embed: 生成稠密和稀疏向量
    Embed->>Milvus: 写入向量索引
    Worker->>PG: 标记文档 ready 和任务 completed
    alt 处理失败
        Worker->>PG: 指数退避后 retry_wait
    else 超过最大次数
        Worker->>PG: 标记 dead 等待人工重试
    end
```

可靠性设计：

- PostgreSQL 的 `document_tasks` 是当前实际任务队列。
- 多 Worker 通过 `FOR UPDATE SKIP LOCKED` 无冲突抢占任务。
- `worker_id`、`lease_expires_at` 和心跳用于识别失联 Worker；过期任务可被恢复。
- 失败任务进入 `retry_wait` 并退避重试，超过最大次数进入 `dead`，接口支持人工重试。
- PostgreSQL 保存可审计的 Chunk 正文与状态；Milvus 只保存可重建的向量索引；MinIO 保存原始文件。

## 5. 权限与安全链路

```mermaid
flowchart LR
    request[用户请求] --> jwt[JWT 验证]
    jwt --> blacklist[Redis 注销黑名单检查]
    blacklist --> tenant[organization_id 租户隔离]
    tenant --> role[知识库成员角色]
    role --> level[用户安全等级]
    level --> team[团队与文档元数据过滤]
    team --> allowed[允许访问的 KB 与文档 ID]
    allowed --> sql[PostgreSQL 查询条件]
    allowed --> vector[Milvus 检索过滤条件]
    sql --> audit[审计日志]
    vector --> audit
```

权限层次：组织租户是第一边界；知识库使用成员角色控制管理操作；检索时进一步按团队、安全等级和文档范围过滤。上传接口还执行白名单格式、声明 MIME、文件真实结构、大小、SHA256 重复检测及 ClamAV 扫描。

## 6. 数据职责

| 组件 | 当前职责 | 是否事实来源 |
| --- | --- | --- |
| PostgreSQL 16 | 用户、组织、权限、知识库、文档、任务、Chunk、会话、消息、引用、收藏、偏好、检索运行、审计 | 是 |
| Redis | 短信验证码、问题缓存、缓存锁、JWT 注销状态、一次性 WebSocket 票据 | 否，短期状态 |

| ClamAV | 上传文件病毒扫描 | 否 |
| DashScope | 问题改写或分类能力、最终回答生成 | 否 |

## 8. 当前实现与原设计文档的差异

1. 原设计图描述了“API 提交问答与文档任务到 Redis Streams，再由 RAG Worker 和文档 Worker 消费”。当前代码中，问答在 WebSocket 所在的 FastAPI 进程内执行，文档任务由 PostgreSQL `document_tasks` 表驱动。
2. 当前只有独立的文档 Worker 启动入口 `backend.app.worker`，没有独立的 RAG Worker 进程入口。
3. Redis 当前承担缓存、验证码、令牌状态和一次性流式票据，不承担文档任务队列。
4. `backend/app/api/workspace.py` 是旧的内存 Mock，未被正式 `api_router` 注册，不应纳入生产主链路。
5. Docker Compose 默认启动数据与安全依赖；后端服务定义仍是注释模板，实际 README 采用宿主机启动 FastAPI 和 Worker。

## 9. 架构判断与后续演进点

- 当前架构适合一期：模块化单体减少分布式复杂度，同时把耗时文档处理隔离为独立 Worker。
- 问答生成与 WebSocket 连接生命周期绑定。若并发增长或需要任务恢复，可把 RAG 执行迁移到可靠队列和独立 Worker，WebSocket 仅负责订阅事件。
- 文档队列表使用 PostgreSQL 已具备抢占、租约和重试能力；在吞吐量未形成瓶颈前，不必为了形式一致迁移 Redis Streams。
- Milvus 索引是派生数据，应持续保留从 PostgreSQL Chunk 全量重建和一致性校验能力。
- `Neo4j` 虽在 Compose 中存在，但未进入当前主链路；没有明确知识图谱需求前不应画入功能架构核心路径。
