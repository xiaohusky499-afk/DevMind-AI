# 企业内部技术知识库智能问答系统 · 任务分工

- 日期：2026-08-21
- 项目类型：RAG MVP（先跑通闭环，后续迭代）
- 团队规模：10 人
- 技术基线：采用模块化 RAG 技术架构（FastAPI + MySQL/BM25 + Redis + Milvus + BGE-M3 + bge-reranker-v2-m3 + DashScope LLM + React）

---

## 1. 项目概述

### 1.1 专属问题（一句话定义）

> 解决「**研发/运维/支持人员在多套内部系统（Wiki、代码库、接口文档、值班手册）中定位技术资料慢、重复提问、新人上手慢**」的问题。

### 1.2 需求真实性依据（公开数据，可复查）

| 证据 | 来源 |
|------|------|
| DXC 用 AI 支持实现 **58% 工单分流**，无需人工介入 | [Resolve 案例](https://resolve.io/customers/dxc-58-percent-deflection-ai-it-support) |
| 企业工单分流行业基准为 15–30%，**38% 企业**已将"IT 自助服务与工单分流"列为优先事项 | [Mosaic AI](https://getmosaic.ai/blog/truth-about-ticket-deflection)、[Aisera](https://www.sgpjbg.com/labelsyh/itzizhufuwuyugongdanfenliucelue.html) |
| Alteryx 用生成式 AI 扩展企业内部 IT 支持 | [Resolve 案例](https://resolve.io/customers/alteryx-ai-virtual-agent-it-support) |
| 内部文档碎片化被称为"每个工程团队隐藏的生产力杀手" | [Doc Holiday](https://doc.holiday/blog/the-hidden-productivity-killer-in-every-engineering-team) |

### 1.3 MVP 量化目标（整体验收线，见第 7 节）

- 高频技术问题自动解答率 ≥ 80%
- 每条回答 100% 附带文档出处引用
- 平均响应时长 < 3 秒（流式首 token < 1.5 秒）
- 低置信度问题 100% 触发转人工兜底（宁可不答，不错答）
- 权限隔离 100% 生效（越权检索命中数为 0）

### 1.4 数据源（企业内部，授权获取）

Confluence/Wiki 技术文档、Git 仓库文档（README/设计文档/接口文档）、值班手册（runbook）、故障复盘报告、脱敏后的历史工单与 FAQ。全部在企业域内处理，数据不出域。

> 先选 **1–2 个团队/系统**试点（如后端组 + 1 个核心系统的文档全量入库），跑通后再推广到全公司。

### 2.3 内部数据合规处理与安全规范

企业场景的核心不是"爬取"，而是**脱敏、权限、不出域**：

**数据处理规则表：**

| 规则 | 具体做法 |
|------|----------|
| 敏感信息脱敏 | 入库前用正则/命名实体识别剔除：密钥、Token、密码、内网 IP/账号、客户数据、个人信息、薪酬数据 |
| 权限分级 | 文档标注 `team`（所属团队）、`security_level`（公开/团队/机密）元数据，检索时按用户权限过滤 |
| 私有化部署 | 向量库、应用、LLM 全部在企业域内；若用外部 LLM API，仅传检索到的文档片段且先经脱敏 |
| 授权边界 | 只入库已获授权的团队/系统文档；不绕过内部系统权限拉取 |
| 审计留痕 | 查询日志记录用户、问题、命中文档，满足合规审计 |

**绝对不做清单：**

- ❌ 不把密钥/生产配置/客户数据/个人信息写入知识库
- ❌ 不采集未授权团队或系统的文档
- ❌ 不用公网大模型传输未经脱敏的内部文档全文
- ❌ 不做基于知识库的自动代码生成/自动运维变更（MVP 外）
- ❌ 不向无权限用户返回受限文档内容

**合规依据：** 数据来源均为企业自有、已授权文档；配合脱敏管线 + RBAC 权限过滤 + 私有化部署 + 审计日志，满足企业内部信息安全基线要求。

### 2.4 FAQ 构建与数据更新

| 事项 | 做法 |
|------|------|
| FAQ 来源 | 历史工单高频问题（脱敏）+ 团队常见问题 + Wiki 已有 FAQ 栏目 |
| 元数据规范 | 所有文档带 `team`、`system`、`doc_type`、`version`、`last_updated`、`security_level` |
| 版本管理 | 文档更新触发增量重建（Confluence/Git webhook 或定时任务），过期文档标记失效 |
| 闭环更新 | 线上差评/转人工问题每周人工复核，确认后补充进 FAQ 与知识库 |

## 4. 任务清单（T1–T14）

> 「可优化点」表格说明每个任务当前技术的局限，以及后续用什么技术优化（MVP 阶段先按当前方案实现，优化点不进 MVP）。
> 「检验标准」按仓库规范只列检验方面与指标，**不写阈值**（阈值统一在第 7 节）。

### T1. 采集整理内部技术文档与 FAQ

- 目标：产出规范化技术文档集与高频 FAQ 表，完成脱敏与权限标注
- 实现技术方案：按 2.1 用 Confluence API / git clone / 系统导出采集文档；按 2.3 执行脱敏管线；FAQ 按 2.4 构建；文档按 team / system / security_level 标注
- 可优化点：

| 当前技术 | 当前问题 | 可优化技术 |
|----------|----------|------------|
| 手工导出 + API 拉取 + 规则脱敏 | 多系统接入重复开发、脱敏规则易漏 | Confluence/Git 原生 webhook 增量同步；LLM + 正则双通道脱敏校验 |

- 对外接口：无（交付物：`internal_kb_qa/data/raw/` 文档集 + `internal_kb_qa/data/faq.xlsx` + 脱敏与权限标注表）
- 检验标准：文档完整性（目标团队/系统全覆盖）、脱敏漏检率、FAQ 条数与人工核对准确率、元数据标注覆盖率
- 对应需求：R1、R3

### T2. 实现多格式文档解析器

- 目标：把 Confluence / Word / Markdown / PDF / OpenAPI 文档统一解析为标准 Document 对象
- 实现技术方案：pymupdf + python-docx + unstructured + BeautifulSoup（Confluence 导出 HTML）+ 已有 Swagger/OpenAPI JSON 解析；复用 `rag_qa/edu_document_loaders/` 现成 loader
- 可优化点：

| 当前技术 | 当前问题 | 可优化技术 |
|----------|----------|------------|
| pymupdf / unstructured 纯文本提取 | 代码块、表格、架构图丢失，解析质量参差 | [MinerU](https://github.com/opendatalab/MinerU)（PDF 转 Markdown/JSON 高质量提取）；代码块单独按语言切分保留结构；架构图走 OCR/多模态模型 |

- 对外接口：
  - `load(file_path: str) -> list[Document]`

    入参：

    | 参数 | 类型 | 必填 | 说明 |
    |------|------|------|------|
    | file_path | string | 是 | 文档文件路径（.pdf / .docx / .md / .html / .json） |

    出参（Document 对象字段）：

    | 字段 | 类型 | 说明 |
    |------|------|------|
    | page_content | string | 解析出的纯文本（代码块保留结构标记） |
    | metadata.source | string | 来源文件/页面名 |
    | metadata.page | int | 所在页码（单页文档为 1） |
    | metadata.doc_type | string | 文档类型：wiki / api / runbook / faq / report |

- 检验标准：各格式解析正确性（文本完整率、乱码率）、代码块结构保留率、失败文档报错可定位
- 对应需求：R1

### T3. 实现文档切分与向量化入库

- 目标：把技术文档切分为语义完整、元数据齐全的 Chunk，并使用 BGE-M3 向量化后写入 Milvus
- 实现技术方案：LangChain RecursiveCharacterTextSplitter + 标题层级切分；代码块按函数/类边界切分（Code Splitter）；元数据新增 `team`、`system`、`version`、`last_updated`、`security_level`；sentence-transformers（BGE-M3）+ pymilvus 写入 collection `internal_tech_kb`，参考 `rag_qa/core/vector_store.py`
- 可优化点：

| 当前技术 | 当前问题 | 可优化技术 |
|----------|----------|------------|
| 固定窗口字符切分 | 代码与配置片段被截断，技术语义被破坏 | 语义分段模型（本仓库已有 `nlp_bert_document-segmentation-chinese-base`）；代码按 AST 函数边界切分；父子块（parent-child chunk）索引 |

- 对外接口：
  - `split(documents: list[Document]) -> list[Chunk]`

    入参：

    | 参数 | 类型 | 必填 | 说明 |
    |------|------|------|------|
    | documents | array | 是 | T2 输出的 Document 列表 |

    出参（Chunk 对象字段）：

    | 字段 | 类型 | 说明 |
    |------|------|------|
    | text | string | 切分后的文本块 |
    | metadata | object | 继承 source / page / doc_type，新增 team、system、version、last_updated、security_level |

  - `insert(chunks: list[Chunk]) -> int`

    入参：

    | 参数 | 类型 | 必填 | 说明 |
    |------|------|------|------|
    | chunks | array | 是 | split() 输出的 Chunk 列表 |

    出参：

    | 字段 | 类型 | 说明 |
    |------|------|------|
    | count | int | 成功写入条数 |

- 检验标准：切分粒度分布、技术语义完整性（代码/配置不截断）、元数据覆盖率、向量维度与 collection 一致性、入库成功率与写入延迟
- 对应需求：R2

### T4. 实现混合检索扩展

- 目标：在 T3 稠密向量入库基础上扩展 BM25 + Dense 混合检索（RRF 融合），Milvus 向量库支持 top-k 检索与权限/系统元数据过滤
- 实现技术方案：Milvus 原生 BM25 全文检索 + Dense 向量检索 + RRF 融合（hybrid search）；collection 沿用 `internal_tech_kb`；检索时强制注入 `team`、`system`、`security_level` 过滤；多租户 partition 隔离；参考 `rag_qa/core/vector_store.py`
- 可优化点：

| 当前技术 | 当前问题 | 可优化技术 |
|----------|----------|------------|
| BM25 + Dense 固定权重 RRF 融合 | 不同问法下关键词与语义权重差异大，术语与口语问法仍有鸿沟 | Query 改写与检索策略路由（T13）；按文档类型/团队自适应调权；文档与代码双路召回 |

- 对外接口：
  - `search(query: str, top_k: int, filter: dict = None) -> list[Hit]`

    入参：

    | 参数 | 类型 | 必填 | 说明 |
    |------|------|------|------|
    | query | string | 是 | 用户问题（可传入 T13 改写后的 query） |
    | top_k | int | 是 | 召回条数 |
    | filter | dict | 否 | 元数据过滤（team、system、security_level，权限过滤必传） |

    出参（Hit 对象字段）：

    | 字段 | 类型 | 说明 |
    |------|------|------|
    | text | string | 命中的文档文本块 |
    | score | float | RRF 融合得分 |
    | metadata | object | 团队、系统、文档类型、版本、更新时间、权限等级 |

- 检验标准：混合检索召回率、关键词与语义混合命中质量、检索延迟、权限过滤正确性（越权命中数）
- 对应需求：R4

### T5. 实现高频技术 FAQ 精确匹配

- 目标：标准高频技术问题走 MySQL + BM25 精确/模糊匹配，命中即秒回，不进 LLM
- 实现技术方案：PostgreSQL + BM25Search，复用 `postgres_qa/`（表结构：问题、标准答案、文档出处、类别、所属团队）
- 可优化点：

| 当前技术 | 当前问题 | 可优化技术 |
|----------|----------|------------|
| BM25 关键词匹配 | 口语化/同义改写命中差（"环境装不上" vs "依赖安装失败排查"） | Sentence-BERT 向量相似度匹配 + 阈值路由；LLM 生成同义问句扩充 FAQ 库 |

- 对外接口：
  - `faq_match(query: str) -> FAQHit | None`

    入参：

    | 参数 | 类型 | 必填 | 说明 |
    |------|------|------|------|
    | query | string | 是 | 用户问题 |

    出参（未命中返回 None）：

    | 字段 | 类型 | 说明 |
    |------|------|------|
    | answer | string | 标准答案 |
    | source | string | 答案出处（文档名/链接） |
    | score | float | 匹配置信度，低于阈值返回 None 走 RAG |

- 检验标准：FAQ 命中率、误匹配率（答非所问比例）、响应延迟
- 对应需求：R3

### T6. 实现意图分类与路由

- 目标：把用户问题分为五类并给出置信度，供主链路路由
- 实现技术方案：微调 BERT 分类器（复用 `rag_qa/core/bert_query_classifier/` 流程），类别：tech / access_request / incident / complaint / chitchat；训练数据用 2.2 的 SMP2017 + 自标注内部语料
- 可优化点：

| 当前技术 | 当前问题 | 可优化技术 |
|----------|----------|------------|
| 单模型微调 | 标注数据少、"技术问题"与"故障上报"边界模糊 | LLM few-shot 分类兜底低置信度样本；主动学习挑难例降低标注量 |

- 对外接口：
  - `classify(query: str) -> Classification`

    入参：

    | 参数 | 类型 | 必填 | 说明 |
    |------|------|------|------|
    | query | string | 是 | 用户问题 |

    出参：

    | 字段 | 类型 | 说明 |
    |------|------|------|
    | category | string | tech / access_request / incident / complaint / chitchat |
    | confidence | float | 分类置信度，低于阈值按 tech（保守路由到带引用的 RAG）处理 |

- 检验标准：分类准确率、各类别召回率、低置信度拒识率
- 对应需求：R5

### T7. 实现重排与生成回答

- 目标：对 T4 召回结果做 bge-reranker 重排 → 带引用 Prompt 生成，输出答案与文档出处
- 实现技术方案：bge-reranker-v2-m3 + DashScope LLM（OpenAI 兼容，流式）；Prompt 要求「仅依据检索到的文档回答 + 标注文档出处 + 文档未覆盖时明确说不知道并建议转人工」；T13 检索策略作为可插拔增强，MVP 先跑通单路，随后接入
- 可优化点：

| 当前技术 | 当前问题 | 可优化技术 |
|----------|----------|------------|
| 单次检索 + 重排 | 跨系统问题（"A 服务调 B 接口报错"）需多文档联动；代码与文档需双路召回 | 文档+代码双路检索融合；接入 T13 查询改写与多路召回策略；系统依赖图谱（GraphRAG：服务→接口→文档→负责人）；Self-RAG 自反思 |

- 对外接口：
  - `rag_answer(query: str, history: list = None) -> RAGResult`

    入参：

    | 参数 | 类型 | 必填 | 说明 |
    |------|------|------|------|
    | query | string | 是 | 用户问题 |
    | history | array | 否 | 最近 N 轮问答，用于补全指代 |

    出参（RAGResult 对象字段）：

    | 字段 | 类型 | 说明 |
    |------|------|------|

## 8. MVP 边界（明确不做）与风险

**MVP 不做**（后续迭代再说）：

- 不做基于知识库的代码自动生成 / 自动修复 / 自动运维变更（高危操作保留人工）
- 不做生产环境操作联动（重启、发布、改配置）
- 不做多模态输入、语音问答
- 不做大模型微调；不扩展到全公司（先 1–2 个团队/系统试点）

**风险与对策：**

| 风险 | 对策 |
|------|------|
| 敏感信息泄露（密钥/客户数据） | 2.3 脱敏管线 + 权限元数据过滤 + 私有化部署 + 审计日志；验收设"越权命中数=0"硬指标 |
| 文档过期误导（改版后旧文档还在库里） | 文档带 `version/last_updated` 元数据，增量重建 + 失效标记 + 回答标注更新时间 |
| 幻觉误导故障处理（on-call 场景代价高） | 低置信度一律转人工；Prompt 强制"不知道就说不知道"；宁可不答，不错答 |
| 多系统文档碎片化 | 统一索引管线接入 Confluence/Git/接口文档，单一检索入口 |
| 权限越权 | 检索链路强制注入 RBAC 过滤（不可绕过），T11 专项验证 |
| 流量峰值 | FAQ 秒回 + Redis 缓存 + LLM 故障降级 FAQ 直回 |
