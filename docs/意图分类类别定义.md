# DevMind-AI 意图分类类别定义与路由说明

> 适用范围：企业内部技术知识库智能问答系统主链路（T6 意图分类）。
> 本文档用于统一分类口径、标注口径和下游路由规则。

## 1. 分类总览

当前共 7 类：

| 编号 | 分类值 | 中文名 |
|------|--------|--------|
| 1 | `tech` | 技术咨询 |
| 2 | `access_request` | 权限 / 账号申请 |
| 3 | `incident` | 故障上报 |
| 4 | `ticket_inquiry` | 工单 / 进度查询 |
| 5 | `complaint_suggestion` | 投诉 / 建议 |
| 6 | `policy_general` | 制度 / 通用知识 |
| 7 | `common` | 闲聊 |

## 2. 分类定义

### 2.1 `tech` 技术咨询

**定义：**
与研发、运维、测试等技术实操直接相关的问题，需要知识库给出排查步骤、配置方法或方案。

**典型问题：**

- Spring Boot 启动报 `Error creating bean with name 'dataSource'`，怎么排查？
- 生产环境 Kafka 消费积压升高，有哪些排查步骤？
- 如何把内网 Maven 私服配置到 `settings.xml`？
- 接口调用返回 503，调用方该怎么处理？
- Docker 部署后端服务的完整步骤是什么？
- Java 并发场景下 ConcurrentHashMap 和 HashMap 怎么选？

**边界：**

- 仅解释概念、不涉及技术操作 → 归 `policy_general`
- 已经发生线上事故 → 归 `incident`

**下游处理：**

1. 先走 FAQ 精确匹配
2. 未命中走 RAG 检索生成，回答必须附文档出处
3. 低置信度时转人工

---

### 2.2 `access_request` 权限 / 账号申请

**定义：**
用户希望开通账号、申请系统权限、申请资源访问权限，或咨询权限申请流程。

**典型问题：**

- 我要申请生产 MySQL 只读权限
- 新同事需要开通 GitLab 和 Jenkins 权限
- 怎么申请测试环境的数据库账号？
- VPN 权限在哪里申请？

**边界：**

- 询问“申请流程” → 仍归 `access_request`
- 账号无法登录但属于技术报错 → 归 `tech`
- 权限申请工单进度查询 → 归 `ticket_inquiry`

**下游处理：**

1. 可检索权限申请文档，告诉用户流程
2. 实际开通权限必须转人工 / 审批，不允许自动开通

---

### 2.3 `incident` 故障上报

**定义：**
线上系统已经发生故障、事故、数据异常、大面积影响，或用户正在报告紧急问题。

**典型问题：**

- 支付服务一直超时，线上订单大面积失败
- 生产数据库主从延迟突然很大
- 刚发布后服务一直重启，需要紧急回滚
- 线上用户无法登录，影响范围很大
- 订单数据好像丢了

**边界：**

- 只是问“如何排查某类故障” → 归 `tech`
- 实际已经发生并影响线上 → 归 `incident`

**下游处理：**

1. 不调用 FAQ / RAG 自动回答
2. 直接转人工 + 创建高优先级工单
3. 即使分类置信度很高，也必须转人工

---

### 2.4 `ticket_inquiry` 工单 / 进度查询

**定义：**
用户查询自己或团队已提交工单的状态、进度、处理人，或催办工单。

**典型问题：**

- 我昨天提的权限申请工单处理到哪了？
- 帮我查一下 TN20260822001 工单状态
- 上周那个故障工单关闭了吗？
- 帮我催一下我的工单

**边界：**

- 申请新权限 → 归 `access_request`
- 报告新故障 → 归 `incident`
- 投诉工单处理慢 → 归 `complaint_suggestion`

**下游处理：**

1. 直接查询 MySQL `tickets` 表
2. 返回工单状态、处理人、更新时间
3. 查不到工单时转人工

---

### 2.5 `complaint_suggestion` 投诉 / 建议

**定义：**
用户表达不满、投诉服务或回答质量，或提出产品改进建议。

**典型问题：**

- 你们这个问答系统太烂了，答案根本不对
- 我要投诉刚才的处理结果
- 建议知识库增加前端页面
- 工单处理太慢了，我要投诉

**边界：**

- 单纯说“答案不对，再查一次” → 可归 `tech`
- 明确表达投诉、不满、建议 → 归 `complaint_suggestion`

**下游处理：**

1. 100% 转人工
2. 写入 `feedback` 表
3. 创建或关联工单

---

### 2.6 `policy_general` 制度 / 通用知识

**定义：**
公司制度、流程、福利等非技术问题，以及不涉及技术实操的概念科普类问题。

**典型问题：**

- 公司年假怎么申请？
- 报销发票有什么要求？
- 入职流程是什么？
- 什么是微服务架构？
- 什么是 Kubernetes，主要解决什么问题？

**边界：**

- 与技术实操相关 → 归 `tech`
- 寒暄问候 → 归 `common`

**下游处理：**

1. 检索通用知识库或模板回复
2. 没有答案时明确说“不知道”，不硬答
3. 复杂制度问题可引导转人工

---

### 2.7 `common` 闲聊

**定义：**
寒暄、问候、天气、笑话等与业务无关的闲聊内容。

**典型问题：**

- 你好
- 今天天气怎么样？
- 讲个笑话
- 你会做什么？

**下游处理：**

1. 模板回复
2. 不检索知识库
3. 不消耗 RAG / LLM 生成资源

## 3. 分类优先级

当一个句子同时命中多类特征时，按以下优先级判断：

```text
incident > complaint_suggestion > access_request > ticket_inquiry > tech > policy_general > common
```

原因：

- `incident` 和 `complaint_suggestion` 属于高风险，必须优先识别并转人工
- `access_request` 和 `ticket_inquiry` 有明显关键词，优先于技术问题
- 无法明确判断时，保守归为 `tech`

## 4. 置信度与兜底规则

| 场景 | 处理 |
|------|------|
| 分类置信度低于阈值 | 降级为 `tech`，走带引用的 RAG |
| LLM 调用失败 / 超时 | 降级为 `tech`，保证主链路不断 |
| LLM 返回格式非法 | 降级为 `tech` |
| `incident` | 无论置信度多高，都转人工 |
| `complaint_suggestion` | 无论置信度多高，都转人工 |
| `access_request` | 只能答流程，不能自动开通权限 |
| `common` | 模板回复，不检索知识库 |

## 5. 分类值约定

代码、Prompt、标注数据中统一使用以下英文值：

```text
tech
access_request
incident
ticket_inquiry
complaint_suggestion
policy_general
common
```

不使用中文分类值，不使用 `chitchat`。

## 6. 下游路由总表

| 分类值 | 路由 |
|--------|------|
| `tech` | FAQ → RAG → 低置信度转人工 |
| `access_request` | 查权限申请文档 → 开通动作转人工 |
| `incident` | 直接转人工 + 高优先级工单 |
| `ticket_inquiry` | 查工单表 |
| `complaint_suggestion` | 直接转人工 + 反馈表 |
| `policy_general` | 通用知识库 / 模板回复 |
| `common` | 闲聊模板回复 |
